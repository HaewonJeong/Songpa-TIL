## 1. 오늘 한 일 요약

오늘은 크게 세 갈래로 진행했다: ①DB 스키마 확정 및 로컬 환경 세팅, ②2차 멘토링 내용 복습·정리, ③실제 REST API(영화/상영회차) 구현 및 인증·인가 설계.

## 2. DB 설계 및 환경 세팅

영화 예매 서비스 스키마(`users`, `genres`, `ratings`, `movies`, `showtimes`, `bookings`, `booking_seats`, `payments`)를 확정했다. 주요 결정 사항:

- **FK 제약조건을 의도적으로 제거**했다. 이유는 최근 트렌드가 MSA(마이크로서비스) 확장을 고려해 DB 레벨 FK보다 애플리케이션 코드로 정합성을 관리하는 방향으로 가고 있기 때문.
- **ENGINE/CHARSET 옵션도 제거** — MySQL 기본값이 이미 InnoDB + utf8mb4라 명시할 필요 없음.
- DB는 최종적으로 **PostgreSQL**로 결정하고 로컬에 설치, pgAdmin으로 `jjcinema_db` 생성.
- **인덱스**는 자주 조회될 컬럼(`status`, `genre_id`, `user_id`, `showtime_id` 등)에 배치, `created_at`에도 인덱스를 붙이는 게 일반적이라는 것을 배움.

**트러블슈팅**:
- pgAdmin에서 Host 필드에 전체 JDBC URL을 잘못 넣어서 접속 주소가 중첩되어 깨진 문제 → Host/Port/Database 필드를 각각 분리해서 입력하도록 수정.
- PostgreSQL 계정명이 MySQL의 `root`가 아니라 `postgres`라는 점 확인.
- Spring Boot `application.yml`에 `spring.datasource.url`, `username`, `password`, `driver-class-name` 설정 및 `ddl-auto: validate` 적용 (이미 SQL로 스키마를 직접 관리하므로 자동 스키마 변경 방지).

## 3. 2차 멘토링 내용 정리 (19개 항목)

엔티티/도메인 폴더 구조(admin vs user 영역 분리), SecurityConfig CORS 설정, `@NoArgsConstructor(access = AccessLevel.PROTECTED)`의 의미(JPA 리플렉션용 기본생성자를 열어두되 외부에서 함부로 못 만들게 제한), 세션·쿠키·Redis 세션·sticky session의 관계, FK를 요즘 안 거는 이유(MSA 확장 고려), 인덱스를 `created_at`에도 흔히 건다는 실무 팁, `ddl-auto: validate`의 의미, DB 락/분산 락 개념, 그리고 `README.md`/`CLAUDE.md`/Plan 모드/Codex 교차검증 같은 Claude Code 활용법까지 전체적으로 복습하고 문서로 정리했다.

## 4. Spring Boot 엔티티/DTO 설계 패턴 학습

- `@NoArgsConstructor(protected) + @AllArgsConstructor(private) + @Builder`(또는 정적 팩토리 메서드 `create()`) 조합으로, 엔티티를 오직 한 가지 정해진 방법으로만 생성하도록 강제하는 패턴을 익힘.
- 엔티티의 `create()`(객체 조립만 담당)와 서비스의 `create()`(객체 생성 지시 + DB 저장 + 응답 변환까지 담당하는 지휘자 역할)의 차이를 명확히 구분.
- 엔티티는 setter 없이 의도가 드러나는 전용 메서드(`update()`, `updateRole()` 등)로만 상태를 바꾸도록 설계.

## 5. REST API 구현

**MovieController / ShowtimeController**에 등록(POST)·수정(PATCH)·조회(GET) API 구현.

- 공통 응답 포맷 `ApiResponse<T>`(`success`, `message`, `data`)를 만들어 모든 API 응답을 통일.
- `@RestControllerAdvice` 기반 `GlobalExceptionHandler`를 만들어 `IllegalStateException`(404), `IllegalArgumentException`(400), `DataIntegrityViolationException`(409), 그 외 예외(500)를 자동으로 깔끔한 JSON 응답으로 변환하도록 처리 — 이전에는 예외가 그대로 스택트레이스와 함께 500으로 노출되던 것을 개선.

**트러블슈팅**:
- `movies.status`가 NOT NULL인데 요청 body에서 누락 → 요청 예시에 `status` 필드 추가로 해결.
- 요청 JSON 키를 스네이크케이스(`movie_id`)로 보내서 자바 필드(`movieId`, 카멜케이스)와 매칭이 안 된 문제 → JSON은 항상 DTO 필드명과 동일한 카멜케이스로 보내야 한다는 것 학습.
- `GET /api/showtimes`에서 필수 `@RequestParam`을 안 붙이고 호출해 에러 발생 → 쿼리스트림과 PathVariable의 차이(필터링 vs 특정 리소스 식별)를 이해.
- `Showtime`/`Movie` 엔티티에 실제 정의된 `update()` 메서드 시그니처와 서비스 코드가 맞지 않아 발생한 컴파일 에러들을 하나씩 맞춰가며 수정.

## 6. 인증/인가 설계

- 관리자 전용 API를 어떻게 구분할지(`/api/admin/...` prefix vs `hasRole("ADMIN")` 개별 매칭) 고민 끝에, 관리자 API 개수가 많지 않은 지금 상황에 맞춰 **URL 안 나누고 `SecurityConfig`에서 `HttpMethod` + 경로별로 `hasRole("ADMIN")` 지정하는 방식**으로 결정.
- `hasRole()`이 내부적으로 `"ROLE_"` 접두어를 붙여서 권한을 비교한다는 것, 그래서 로그인 시 `UserDetailsService`에서 DB의 `role` 값을 `GrantedAuthority`로 변환해줘야 한다는 것을 학습.
- 관리자 계정은 회원가입 API로 직접 만들 수 없게(보안상 당연한 설계) 하고, 대신 ①첫 관리자는 DB에 직접 SQL로 role을 `ADMIN`으로 변경, ②이후 관리자는 `PATCH /api/users/{userId}/role`(관리자 전용) API로 승격시키는 구조로 설계.

## 7. 좌석 조회 & 동시성 설계 (설계 완료, 구현 진행 중)

좌석을 8열(1~8) × 6행(A~F), 총 48석으로 고정 설계. DB에 좌석 마스터 테이블을 따로 두지 않고 코드에서 좌석 코드를 생성하는 방식으로 결정 (상영관마다 좌석 배치가 달라지는 경우엔 `theaters`/`seats` 테이블 분리가 필요하다는 것도 학습했지만, 지금 요구사항엔 불필요하다고 판단해 제외).

동시성 문제(같은 좌석을 두 사람이 동시에 예매)는 `booking_seats` 테이블의 `UNIQUE(showtime_id, seat_code)` 제약을 활용해 DB 레벨에서 자동으로 막고, `DataIntegrityViolationException`을 `GlobalExceptionHandler`에서 409(Conflict)로 응답하도록 설계.

## 8. 회고

- 하루 동안 DB 설계→환경 세팅→API 구현→보안 설계까지 전체 백엔드 흐름을 한 바퀴 돌았다.
- 특히 CLI로 생성된 엔티티 코드(정적 팩토리 메서드, private 생성자 등)를 직접 읽고 서비스 코드와 맞춰나가는 과정에서 에러가 잦았지만, 그때마다 실제 시그니처를 확인하고 맞추는 습관을 들인 게 도움이 됐다.
- 관리자 API 구조(URL 분리 vs hasRole)처럼 정답이 없는 설계 결정 앞에서 여러 번 고민했는데, "지금 규모/시간에 맞는 선택"이라는 기준으로 판단하는 연습을 했다.
