**2. 백엔드 배포 (Render)**
- Render PostgreSQL DB 생성
- 백엔드 Dockerfile 작성 (Gradle 빌드 스테이지 + JRE 실행 스테이지로 분리한 멀티스테이지 빌드)
- 배포 중 발생한 에러 해결:
  - DB 연결 실패 → `application.yml`의 환경변수 이름이 Render 대시보드 설정값과 불일치했던 것을 발견, `${DB_URL}` 형태로 통일
  - `url`이 `localhost`로 하드코딩되어 있던 부분을 환경변수 기반으로 수정
  - CORS 에러 → `SecurityConfig`의 `allowedOrigins`에 배포된 프론트 도메인 추가
  - 세션 쿠키가 배포 환경에서 전달되지 않는 문제 → 프론트/백엔드가 서로 다른 도메인이라 `SameSite=None; Secure` 쿠키 설정 추가

**3. 프론트엔드 배포 (Vercel)**

- 환경변수(`NEXT_PUBLIC_API_BASE`)로 백엔드 API 주소 연결

**4. 데이터 세팅 및 검증**
- 장르/관람등급 등 기준 데이터 시드

**5. 배포 후 발견한 버그와 수정**
- 좌석 임시선점 카운트다운이 뜨자마자 "만료됨"으로 표시되는 버그 발견 → 원인은 서버가 내려주는 시간이 타임존 표기(UTC `Z`) 없이 내려와서, 브라우저가 이를 로컬시간(KST)으로 잘못 해석해 9시간 오차가 발생한 것. 클라이언트 자체 시계 기준으로 만료 시각을 계산하는 방식으로 수정.
- Safari에서 로그인 후 세션이 유지되지 않는 문제 발견 → 원인은 Safari의 ITP(Intelligent Tracking Prevention)가 프론트(`vercel.app`)와 백엔드(`onrender.com`)처럼 서로 다른 도메인 간 쿠키를 크로스사이트 쿠키로 간주해 기본 차단하기 때문. 근본 해결책으로 Next.js `rewrites`를 이용해 브라우저가 백엔드를 직접 호출하지 않고 프론트 서버가 대신 프록시하도록 구조를 변경(동일 출처처럼 보이게 만들어 ITP 자체가 개입하지 않게 함) — 적용 및 검증 진행 중.

## 트러블슈팅에서 배운 점
- 배포 환경에서는 환경변수 이름이 애플리케이션 코드와 배포 플랫폼 설정 양쪽에서 정확히 일치해야 하며, 하나라도 다르면 로컬에서는 재현되지 않는 에러가 발생한다.
- 프론트와 백엔드가 서로 다른 도메인에 배포되면 CORS뿐 아니라 세션 쿠키의 `SameSite` 정책, 브라우저별 쿠키 차단 정책(Safari ITP 등)까지 복합적으로 고려해야 한다.
- JavaScript의 `Date` 파싱은 타임존 정보가 없는 문자열을 브라우저의 로컬 시간대로 해석하므로, 서버-클라이언트 간 시간 데이터를 주고받을 때는 반드시 UTC임을 명시해야 한다.
- Render 무료 티어의 웹 서비스는 디스크가 임시(ephemeral) 저장소라, 재배포하면 업로드했던 파일(이미지 등)이 초기화된다는 것을 실제로 겪고 나서 알게 되었다.

## 느낀 점

# 2026-09-05 멘토링 추가 작업 기록

## 오늘 한 일 요약
JJCinema 프로젝트를 실제 서비스처럼 배포하고, 배포 환경에서만 드러나는 문제들을 하나씩 진단·해결하는 데 하루를 썼다.

## 배포 과정
Render(백엔드 + PostgreSQL)와 Vercel(프론트엔드) 조합으로 무료 배포를 진행했다. 백엔드는 Gradle 빌드용 스테이지와 실행용 JRE 스테이지를 나눈 멀티스테이지 Dockerfile로 이미지를 구성했고, Render Postgres에 연결했다.

배포 초반에는 `application.yml`에 적어둔 환경변수 이름과 실제 배포 플랫폼에 등록한 이름이 어긋나 있어서 DB 인증 실패가 반복됐다. 하드코딩되어 있던 로컬 DB 주소도 함께 손봐서, 환경변수가 없을 때는 로컬 기본값으로 떨어지도록 정리했다.

프론트를 Vercel에 올린 뒤에는 CORS 에러가 났고, 백엔드의 허용 origin 목록에 배포된 프론트 주소를 추가해 해결했다. 이어서 로그인은 되는데 이후 요청에서 세션이 유지되지 않는 문제가 나타났는데, 원인은 프론트와 백엔드가 서로 다른 도메인이라 세션 쿠키가 기본 정책상 전달되지 않는 것이었다. `SameSite=None; Secure`로 쿠키 속성을 조정해 크롬에서는 정상 동작하도록 만들었다.

## 배포 후 발견한 두 가지 버그
서비스를 실제로 사용해보다가 두 가지 문제를 추가로 찾았다.

첫째, 좌석을 선택하면 임시 선점 카운트다운이 뜨자마자 곧바로 "만료됨"으로 표시됐다. 원인을 추적해보니 서버가 내려주는 시간 문자열에 UTC 표기(`Z`)가 없어서, 브라우저가 이를 한국 로컬 시간으로 잘못 해석해 9시간의 오차가 발생하고 있었다. 서버 시간 문자열을 파싱하는 대신, 클라이언트 자신의 시계를 기준으로 만료 시각을 계산하도록 로직을 바꿔 근본적으로 해결했다.

둘째, 다른 사람이 Safari(맥)에서 접속했을 때 로그인 후 예매 시도가 전부 403으로 실패하는 것을 확인했다. 조사해보니 Safari의 ITP(Intelligent Tracking Prevention)가 서로 다른 도메인 간 쿠키를 크로스사이트 쿠키로 간주해 기본적으로 차단하고 있었다. 커스텀 도메인으로 도메인 자체를 통합하는 방법도 검토했지만 시간이 오래 걸려서, 대신 Next.js의 rewrites 기능으로 브라우저가 항상 프론트 서버에만 요청하고 그 뒤에서 백엔드로 프록시하도록 구조를 바꿨다. 이러면 브라우저 입장에서는 모든 요청이 동일 출처로 보여 ITP가 개입할 이유 자체가 없어진다. 실제 macOS Safari 환경으로 원격 테스트를 해본 결과 로그인과 예매가 정상적으로 동작하는 것까지 확인했다.

## 락 전략 성능 비교 실험
기존에 구현해둔 비관적 락(PESSIMISTIC_WRITE) 외에, 벤치마크 전용으로 낙관적 락(@Version) 방식도 추가 구현해 k6로 부하 테스트를 진행했다. 좌석 1개에 동시 사용자 100명을 몰아넣고, 두 방식의 응답 시간·처리량(TPS)·충돌 발생 건수를 실측 비교했다. 좌석이 1개뿐이라 두 방식 모두 성공은 1건, 실패는 99건으로 동일했지만, 비관적 락은 락을 기다리는 시간만큼 응답이 느려지고, 낙관적 락은 응답은 빠른 대신 버전 충돌(OptimisticLockException)이 그만큼 많이 발생하는 특성 차이를 데이터로 직접 확인할 수 있었다.

## 배운 점
같은 코드라도 로컬과 배포 환경은 완전히 다른 문제를 드러낸다는 것을 하루 종일 체감했다. 환경변수 이름 하나, 도메인 하나, 브라우저 하나가 달라질 때마다 새로운 실패 지점이 나타났고, 그때마다 원인을 좁혀가는 과정 자체가 좋은 훈련이 됐다. 특히 Safari ITP 이슈는 "완벽한 해결책"과 "지금 가능한 해결책" 사이에서 현실적인 선택을 해야 했던 경험이라 기억에 남는다.
