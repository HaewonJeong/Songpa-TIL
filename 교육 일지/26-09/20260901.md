## 1. 오늘 한 일 요약

어제(102일차)까지는 백엔드 결제 API를 만드는 데 그쳤는데, 오늘은 **백엔드 잔여 구현을 마무리하고 프론트엔드(`mockApi.js`)의 모든 함수를 실제 백엔드 API 호출로 교체**했다.(3건 남음) 로그인부터 회원가입, 영화·상영·좌석·예매·결제·관리자 화면까지 전 화면을 순서대로 하나씩 연동하면서, 그 과정에서 드러난 백엔드 설계 구멍(누락된 API, DTO 필드 부족, 동시성 설계 미흡)을 그때그때 같이 고쳤다. 마지막엔 좌석 동시성 락을 "상영 단위"에서 "좌석 단위"로 재설계했다.

## 2. 백엔드 잔여 구현

- **Admin API 연결**: `AdminController`가 빈 스텁이라 서비스 로직(`getStats`, `getShowtimes`, `getUsers`, `updateUser`)은 다 있는데 엔드포인트가 하나도 없던 것을 확인하고 4개 엔드포인트(`GET /api/admin/stats`, `/showtimes`, `/users`, `PATCH /api/admin/user/{id}`) 연결.
- **`SecurityConfig`**: `/api/admin/**`에 `hasRole("ADMIN")` 규칙 추가(안 그러면 일반 회원도 관리자 API 호출 가능), `/api/genres`·`/api/ratings`의 `DELETE`에 대한 권한 규칙 누락 발견 후 추가, CORS 설정(`CorsConfigurationSource` 빈 + `.cors(Customizer.withDefaults())`) 추가.
- **로그인 응답 개선**: `POST /api/auth/login`이 문자열 대신 `UserResponse`(id/name/email/role)를 반환하도록 변경. 로그인 실패(비번 오류)/비활성 계정을 `AuthenticationException`으로 잡아 401로 처리하는 핸들러 추가.
- **이메일 중복확인 API 신규**: `GET /api/auth/check-email?email=`을 새로 만들어 회원가입 폼에서 실시간 중복확인이 가능하게 함.
- **예매 상세 조회 API 신규**: `GET /api/bookings/{id}`가 원래 없었다는 것을 뒤늦게 발견 — `BookingDetailResponse`(영화 제목/포스터/상영정보/결제상태까지 합친 응답)를 새로 설계해서 추가. `GET /api/bookings/me`(내 예매 목록)도 같은 DTO로 교체.
- **상영 개별 수정 API 신규**: `PATCH /api/showtimes/{id}`(일괄수정만 있고 개별수정이 없었음)를 위한 `ShowtimeUpdateRequest` + 서비스 메서드 + 컨트롤러 추가.
- **HOLD(임시선점) 5분 만료 로직**: 처음엔 백엔드에 아예 없다는 걸 발견(좌석을 선점만 해두고 방치하면 영구히 안 풀리는 버그) → `getSeatMap()`/`pay()`에 만료 체크 추가.
- **결제 실패 시 정책 변경**: 처음엔 결제 실패하면 곧바로 예매 취소 + 좌석 해제하도록 했다가, "실제 영화관 앱은 결제 실패해도 좌석을 계속 들고 있다가 재시도할 수 있게 한다"는 실사용 경험을 반영해 정책을 바꿈 — 실패해도 `Booking`은 `HELD` 그대로 유지하고 `Payment` 레코드도 안 남기도록(재시도 시 `payments.booking_id` UNIQUE 제약과 충돌 안 나게) 수정.

## 3. 좌석 동시성 락 재설계 — showtime 단위 → 좌석 단위

기존엔 `Showtime` 행 하나에 `@Lock(PESSIMISTIC_WRITE)`를 걸어서 "같은 상영에 대한 모든 예매 요청을 한 줄로 세우는" 방식이었다. 정확성은 100% 보장되지만, 서로 다른 좌석을 고른 사람들도 불필요하게 순서를 기다려야 한다는 단점이 있었다.

**재설계 내용**:
- `Seat` 엔티티(신규) — 상영 등록 시 좌석 40개(A1~E8)를 미리 DB 행으로 생성. `occupied`(점유 여부) + `heldAt`(선점 시각, null이면 결제완료로 영구 점유 또는 빈 자리) 필드로 상태 표현.
- `SeatRepository.findForUpdate(showtimeId, seatCode)` — 좌석 1건 단위로 `PESSIMISTIC_WRITE` 락.
- 여러 좌석을 한 번에 예매할 때 **좌석 코드를 정렬한 순서대로 락을 걸어 데드락을 방지**하는 패턴을 배움(A가 [A1,A2], B가 [A2,A1] 순서로 락 걸면 서로 물려서 데드락 나는 상황을 막기 위함).
- `getSeatMap()`이 `booking_seats` 존재 여부 대신 `Seat.isAvailable(5분)`로 판단하도록 바뀌면서 오히려 코드가 더 단순해짐.
- https://github.com/Ogu-Family/MIML_backend/blob/main/src/main/java/com/miml/c2k/domain/seat/Seat.java

## 4. 프론트엔드 — `mockApi.js` 전체를 실제 API로 교체

원래 계획대로 `mockApi.js` 함수를 하나씩 순서대로 실제 `fetch` 호출로 바꿨다. 화면(컴포넌트) 코드는 거의 안 건드리고, API 함수 내부만 교체하는 방식이 실제로 잘 통했다.

- **인증**: `login`, `signup`(회원가입은 세션을 안 만들어서 가입 성공 후 로그인 페이지로 보내도록 화면 흐름도 변경, 토스트 메시지 추가), `checkEmailAvailable`.
- **회원가입 폼 검증 강화**: 닉네임(1~8자 영문/한글/숫자), 이메일 형식(정규식), 비밀번호(8~15자, 영문 소문자+특수문자) 검증을 프론트에서 직접 구현. 브라우저 자체 유효성검사(`<input type="email">`)가 우리 커스텀 에러 메시지보다 먼저 튀어나오는 문제를 발견 → `<form noValidate>`로 해결.
- **회원관리**: `getAllUsers`, `updateUser`.
- **영화**: `getMovies`, `getMovie`, `getAllMovies`, `updateMovie`, `createMovie` — 백엔드가 `genreId`/`ratingId`(숫자)만 주는데 화면은 `'SF'`, `'12세'` 같은 이름을 쓰기 때문에, 앱 시작 시 `/api/genres`·`/api/ratings`를 불러와 **id↔이름 양방향 사전**을 만들어 매핑하는 패턴을 반복적으로 사용. 관리자 영화 등록 폼도 하드코딩된 장르/등급 드롭다운 대신 **DB에서 실제 목록을 불러와 렌더링**하도록 개선.
- **상영시간표/좌석맵**: `getShowtimes`, `getSeatMap` — 좌석맵은 백엔드가 상영 정보를 따로 안 줘서 좌석 API와 상영 조회 API 두 개를 동시에(`Promise.all`) 불러와 합치는 방식으로 구현.
- **예매/결제**: `createBooking`, `getBooking`, `createPayment`, `getMyBookings`, `cancelBooking` — 상태값 매핑(`HELD`/`CONFIRMED`/`CANCELLED` ↔ `결제대기`/`예매완료`/`취소됨`) 반복.
- **관리자 상영관리**: `getAllShowtimesAdmin`, `createShowtime`, `getShowtime`, `updateShowtime`, `updateShowtimesBulk`.

**포스터 이미지 처리 원리**: `FileReader.readAsDataURL()`로 이미지를 base64 문자열(`data:image/png;base64,...`)로 변환해 그대로 백엔드 `movies.poster_base64`(TEXT 컬럼)에 저장하는 방식임을 이해함 — 별도 파일 서버 없이 DB에 이미지 자체를 문자열로 넣는 단순한 구조.

## 5. 트러블슈팅

| 증상 | 원인 |
|---|---|
| 로그인 페이지에서 이상한 브라우저 팝업(`'@' 기호를...`) | `<input type="email">`의 브라우저 자체 유효성검사가 커스텀 검증보다 먼저 실행됨 → `noValidate` 추가로 해결 |
| 회원가입 완료 토스트가 뒤로가기할 때마다 반복해서 뜸 | `location.state`가 히스토리에 남아있어서 재발 → 토스트 띄운 직후 `navigate(path, {replace:true, state:{}})`로 상태 제거 |
| CORS 설정 후에도 안 됨 | `setAllowedOrigins`를 두 번 호출(`setAllowedMethods`를 오타로 또 `Origins`라고 씀) — 실제 origin이 통째로 덮어써짐 |
| `PaymentRepository.findBookingByBookingId`가 이상해 보임 | Spring Data JPA는 `find`와 `By` 사이 단어를 무시한다는 규칙을 다시 확인, 실제로는 정상 동작(지난번 잘못 짚었던 것 정정) |
| `AdminController`/`BookingController`의 API 응답 포맷이 서로 다름 | 일부 컨트롤러(`Auth`, `Genre`, `Rating`)는 `ApiResponse`로 안 감싸고 원본을 그대로 반환 — 프론트에서 매번 어떤 포맷인지 확인해야 했음 |
| 예매 후 결제 페이지에서 데이터가 안 뜸 | `GET /api/bookings/{id}` 자체가 백엔드에 없었음 — 신규 API 추가로 해결 |
| 5분 지나도 좌석이 안 풀림(처음엔 버그로 오해) | 원인은 두 가지였음. ① `getBooking`/`createPayment`가 어느 시점에 실수로 mock 버전으로 되돌아가 있었음. ② "← 좌석 선택" 버튼은 원래 즉시 취소하도록 의도된 동작이라 5분 타이머와 무관했음 |

## 6. 오늘 배운 개념

- **좌석 단위 비관적 락 + 정렬 순서 락**으로 데드락을 방지하는 패턴.
- **`data:` URL**은 실제 주소가 아니라 데이터 자체를 담은 문자열이라, 브라우저가 요청 없이 바로 디코딩해서 렌더링한다는 것.
- 백엔드 DTO는 "이 동작에 뭐가 필요한가" 기준으로 좁게 설계되기 쉽고, 프론트(특히 mock 시절부터 만들어진 화면)는 필요한 걸 다 담아서 설계되기 때문에 **연동하면서 필드 부족이 드러나는 건 계획 실패가 아니라 정상적인 통합 과정**이라는 것.
- 결제 실패 시 좌석을 바로 풀지, 재시도 기회를 줄지는 **정답이 없는 정책 결정**이고, 실제 서비스 사용 경험에 비춰 판단하는 게 중요하다는 것.
