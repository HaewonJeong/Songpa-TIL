## 1. 오늘 한 일 요약

어제(103일차)까지 전체 API 연동을 끝냈고, 오늘은 **남아있던 마지막 기능 2개(세션 복원/로그아웃, 환불 처리)를 마무리**하고, 그 과정에서 좌석 동시성 로직의 **진짜 근본 원인 버그**를 하나 더 찾아서 고쳤다. 오후엔 QA 테스트 케이스 문서를 Notion에 작성하며 실제로 화면을 눌러보는 과정에서 여러 자잘한 착오(테이블 혼동, 툴 설정 이슈 등)를 하나씩 정리했다.

## 2. 백엔드 마무리 기능 2개

- **`GET /api/auth/me` / `POST /api/auth/logout` 신규 구현**: 지금까지는 새로고침 시 로그인 유지가 프론트 `sessionStorage`만 믿는 방식이었음 — 서버 세션이 실제로 유효한지 확인을 안 하고 있었다. `/me`로 서버에 직접 "나 로그인 상태 맞아?"를 물어보게 바꾸고, `/logout`이 실제로 `HttpSession.invalidate()`를 호출하도록 구현. `SecurityConfig`에서 `/api/auth/me`만 예외적으로 `authenticated()`를 앞에 둬서(순서 중요) 로그인 필요하게 만듦.
- **결제완료(CONFIRMED) 예매 취소 시 환불 처리**: `BookingService.cancel()`이 좌석/예매만 처리하고 결제는 손 안 대던 것을 발견 → 취소 전에 `wasConfirmed` 여부를 기억해뒀다가, 결제완료였던 경우에만 `Payment.refund()`(status를 `REFUNDED`로 변경)를 호출하도록 수정. `Payment` 엔티티엔 이 메서드가 없어서 새로 추가.

## 3. 좌석 동시성 — 진짜 근본 버그 발견 (3번째 라운드)

어제 좌석 단위 락으로 재설계한 뒤에도 `booking_seats_showtime_id_seat_code_key` UNIQUE 위반이 계속 재발했다. 처음 두 번은 "예전 테스트 데이터 찌꺼기"로 판단해 SQL로 수동 정리했는데, 세 번째 재발했을 때 진짜 원인을 찾았다:

> `hold()`가 좌석이 "예약 가능"인지 `Seat.isAvailable()`(5분 지났으면 사실상 빈 자리로 침)만 확인하고 통과시키는데, **그 좌석을 예전에 물고 있던 옛날 `booking_seats` 행을 안 지우고 새 행을 또 넣으려 함.** `Seat` 테이블은 시간 계산으로 "빈 자리"라고 판단하는데(lazy expiry), `booking_seats`는 실제 행이 그대로 남아있어서 새 INSERT가 UNIQUE 제약에 걸리는 구조였다.

**해결**: `hold()`에서 좌석이 `isAvailable()==true`로 확인된 시점에, 그 판정은 "지금 이 좌석엔 유효하게 점유 중인 게 없다"는 뜻이므로 — 남아있는 옛날 `booking_seats` 행은 전부 안전하게 정리해도 된다는 불변조건을 이용해 `cleanupStaleBookingSeat()` 헬퍼를 추가. 좌석을 새로 잠그기 직전에 이 정리를 호출해서, 만료된 HOLD가 남긴 잔여 데이터를 그 자리에서 자동으로 청소하도록 만들었다. 이후로는 수동 SQL 정리 없이도 재발하지 않음을 확인.

**덤으로 발견한 죽은 코드**: `ShowtimeRepository.findByIdForUpdate()`(어제 재설계 전, 상영 단위 락을 걸던 메서드)가 프로젝트 어디에서도 안 쓰이고 있는 걸 발견 — `hold()`가 이제 락 없는 `findById()`로 바뀌었기 때문. 삭제 대상으로 표시해둠.

## 4. QA 테스트 케이스 작성

Notion에 "🧪 QA 테스트 케이스" 페이지를 새로 만들어 화면/기능별로 50개 이상의 테스트 케이스를 정리했다 (인증, 영화, 상영시간표, 좌석·예매, 결제, 내예매관리, 관리자 4개 화면, 공통 예외처리). 특히 더블부킹 테스트(계정 2개로 같은 좌석 동시 예매 시도)와 권한 테스트(남의 예매 조회/취소 시도 시 403)를 핵심 케이스로 넣었다.

실제로 테스트 케이스를 하나씩 실행해보면서 발견한 것들:
- 결제완료 예매를 취소했는데 `payments` 테이블에서 엉뚱한 `booking_id`를 보고 당황 — `bookings.id`와 `payments.booking_id`가 서로 다른 예매를 가리킬 수 있다는 것(각자 독립적인 시퀀스)을 놓쳤던 것. 결제를 안 하고 취소한 예매는애초에 `payments`에 행이 안 생기는 게 정상이라는 걸 재확인.
- 상영 10건 일괄 등록 후 "좌석 40개가 `booking_seats`에 안 생긴다"고 착각 — 상영 등록 시 자동 생성되는 건 `seats` 테이블(좌석 정의)이고, `booking_seats`는 실제 예매가 있을 때만 생기는 별개 테이블이라는 걸 다시 정리.
- 일반 회원으로 관리자 페이지 접속 시 리다이렉트가 2단계로 일어나는 걸 발견하고 원리를 파악: `AdminRoute`가 권한 없으면 `/movies`로 보내고, `/movies` 자체도 "들어오면 `now-showing`으로 리다이렉트"하는 규칙이 있어서 연쇄적으로 `/movies/now-showing`까지 이동함.

## 5. 하지 않기로 결정한 것

- **극장(Theater) 테이블 분리**: "관마다 좌석 배치가 다르면 어떡하냐"는 질문에서 시작된 논의. 실제로 다른 팀 프로젝트(MIML)도 같은 이유로 관 공통 배치로 단순화해둔 걸 확인했었고, 지금 시점에 추가하면 `Showtime` 관련 DTO 전부와 관리자 상영 등록 폼, `mockApi.js` 상영 함수 6개까지 건드려야 하는 데다 기존 상영 데이터 마이그레이션까지 필요해서 — QA·배포를 앞둔 지금은 하지 않기로 결정.
- **테스트 코드(JUnit) 전체 작성**: 서비스/컨트롤러 전체 커버리지는 시간 대비 효율이 낮다고 판단해 보류. 다만 원래 계획에 있던 **동시 예매 JUnit 테스트(두 스레드, 같은 좌석)** 하나는 이 프로젝트의 핵심 증명 자료로서 가치가 커서, 시간이 되면 작성하기로 남겨둠 (아직 미작성).

## 6. 트러블슈팅

| 증상 | 원인 |
|---|---|
| `Unsafe query: 'Delete' statement without 'where' clears all data` | DB 툴(DataGrip 추정)의 안전모드가 `WHERE` 없는 대량 삭제를 차단 — `WHERE true`로도 막힘, 결국 안전모드 토글/TRUNCATE로 우회 |
| Postman에서 `/api/bookings/83%0A` 요청 → 400 | URL을 복사·붙여넣기 하면서 끝에 줄바꿈 문자가 같이 들어감 — `Long` 타입 바인딩 실패로 컨트롤러 도달 전에 Spring 기본 에러 포맷(400)으로 떨어짐 |
| 결제완료 예매 취소했는데 예상한 `payments` 행이 안 보임 | 결제를 실제로 안 하고 취소한 예매였음(`booked_at`이 null) — 결제 안 한 예매는 애초에 `payments` 행이 없는 게 정상 |
| 상영 등록해도 `booking_seats`에 40개가 안 생김 | `booking_seats`가 아니라 `seats` 테이블에 자동 생성되는 것이었음 — 두 테이블의 역할을 혼동 |
| 좌석 동시성 UNIQUE 위반이 세 번째 재발 | 이전 두 번은 데이터 정리로 임시 해결했지만, 세 번째에 `hold()`가 만료된 좌석의 잔여 `booking_seats`를 안 지우는 근본 버그를 발견하고 코드로 해결 |

## 7. 오늘 배운 개념

- **lazy expiry(지연 판정)를 쓸 때는 "판정에 쓰는 테이블"과 "실제 데이터가 남아있는 테이블"이 분리되어 있으면, 판정만 고치고 잔여 데이터 정리를 빠뜨리기 쉽다** — `Seat.isAvailable()`은 시간 계산만으로 판정하지만, 그 판정이 "안전하다"고 보장해주는 시점(= 정리해도 되는 시점)을 놓치면 이번처럼 재발한다.
- **DB 관리 툴의 안전장치(안전모드)**는 SQL 문법이 아니라 툴 설정이라, `WHERE`절을 아무리 그럴듯하게 써도 못 뚫는 경우가 있다는 것.
- 같은 도메인의 여러 테이블(`bookings`/`payments`/`seats`/`booking_seats`)이 **각자 다른 역할과 다른 생명주기**를 가진다는 걸 명확히 구분해야, "왜 여기 데이터가 없지?"를 버그가 아니라 정상 상태로 판별할 수 있다.
- 리액트 라우터의 리다이렉트는 여러 단계를 거칠 수 있고, `replace: true`를 쓰면 중간 경유지가 히스토리에 안 남는다는 것.
